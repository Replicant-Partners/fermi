### 2. `eval_brier.rs` latent bug

Lines 91 and 108 reference `agents.owner_id`. That column does
**not exist** on the `agents` table — the correct column is
`agents.user_id` (added by mig 006).

```sql
-- eval_brier.rs:91-93 (current, broken):
OR f.owner_id IN (
  SELECT owner_id FROM agents WHERE agent_id = $1
)

-- eval_brier.rs:108 (current, broken):
JOIN agents a ON a.owner_id = f.owner_id
```

Post-mig-165, `fermi_forecasts.owner_id` is TEXT and `agents.user_id`
is TEXT. So the fix is straightforward:

```sql
OR f.owner_id IN (
  SELECT user_id FROM agents WHERE agent_id = $1
)
...
JOIN agents a ON a.user_id = f.owner_id
```

Only fires on the agent Brier calibration lookup — not a hot path.
Confirmed not user-facing today, but will 500 the calibration UI when
someone opens an agent's calibration panel.

## Pitfalls

1. **Do not blindly ship without an exhaustive audit.** v0.10.3
   through v0.10.12 patched observed sites one at a time. That's
   what caused Ivan's frustration. v0.10.13 broke the pattern by
   grepping for every occurrence of the bug shape (`::uuid` casts
   and `Uuid` type reads on fermi owner columns) before making a
   single edit. Do this every time:

   ```bash
   grep -rn "::uuid" src/handlers/ --include="*.rs"
   grep -rn "owner_id: Uuid" src/handlers/ --include="*.rs"
   grep -rnE "u\.id\s*=\s*[a-z_]+\.owner_id" src/handlers/ --include="*.rs"
   ```

   The residuals after v0.10.13 are all verified-safe (teams.id,
   session_id, `unnest($1::uuid[])`, the runtime cast-picker in
   admin_rbac). Any new hit is a real bug.

2. **Do not assume "declared schema == deployed schema."** The
   fermi_* tables' `owner_id` FK drifted from `users(user_id)` to
   `users(id)` at some point (probably a manual Neon SQL editor
   patch during an earlier debugging session). This drift went
   undetected for potentially months because Ivan (`user_id = id`
   by coincidence via mig 004b backfill) never hit it. Every schema
   check must query `pg_constraint` for the actual deployed state,
   not trust migration files. This is the reason v0.11.0 exists.

3. **The `.gitmsg-*` files accidentally get committed.** The
   protocol is:

   ```bash
   git add -A && git commit -F .gitmsg-<ver>
   git rm .gitmsg-<ver> && git commit --amend --no-edit
   git tag -a v<ver> -m "..." && git push origin main --follow-tags
   ```

   Every release. If you see a `.gitmsg-*` file in `git ls-tree
   HEAD`, the previous release forgot the amend.

4. **Railway `/api/health` returns `"unknown"` commit on this deploy.**
   `RAILWAY_GIT_COMMIT_SHA` env vars aren't set. To verify a
   deployment is live post-push, use behavioural probes (curl
   endpoints that would 500 on the pre-fix version, or query
   `pg_get_constraintdef` for a known-changed FK) rather than the
   health endpoint's commit field.

5. **Console binary version lag.** The Tauri auto-updater checks on
   startup only. If Ilabra reports "still failing," first confirm
   sidebar version chip — she may need to restart the console. As
   of 2026-08-01 03:26 UTC her sidebar showed `v0.10.13 — up to
   date`, so v0.10.14 pull requires a restart.

6. **502 during Railway rolling deploys is normal.** After pushing
   v0.10.13 we saw ~3 minutes of HTTP 500 (old container still
   serving) → 502 (rolling restart) → 200 (new container up).
   Don't panic if you see 502 within 5 minutes of a push.

7. **Two "Ivan Labra" accounts exist.** Don't conflate them:

   | Email | user_id | Purpose | Token env |
   |---|---|---|---|
   | ivan@axolotl.partners | 2e644008-f5c7-47c5-854c-3801df9879cc | Admin | (Ivan admin key) |
   | ilabra@gmail.com | 0c640559-f926-43b5-b629-2a776f5ed24b | Dev | `$ILABRA_TOKEN` |
   | mo@axolotl.partners | 010e541a-6273-4de5-885c-bd1cc3e0f19c | Non-admin test | `$MO_TOKEN` |

   Both "Ivan Labra"s have `display_name = "Ivan Labra"` — the only
   disambiguator is the `user_id` UUID.

8. **UI "empty state" ≠ empty data.** Ilabra's "0 forecasts / 0
   portfolios" was a `list_forecasts_handler` 500, not missing
   rows. Always curl the API endpoint directly before concluding
   data is gone. See v0.10.13 for the diagnostic sequence.

9. **The chip vs Ctrl+P publish inconsistency was invisible
   during the RBAC-broken era.** Because nothing published
   successfully, no one saw that the chip took a different code
   path than the keybind. General lesson: features that "sometimes
   worked, sometimes didn't" during a broken era may hide
   inconsistencies that only surface once the underlying is
   fixed. v0.11.0's e2e test should exercise both trigger paths
   for every action.
