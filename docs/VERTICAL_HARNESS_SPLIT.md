# Vertical / Harness Split

**Companion to** `docs/AGENT_MODEL.md`. AGENT_MODEL covers what an
agent is and how the substrate works. This doc covers how the
substrate (the ABW harness) relates to the verticals that consume
it.

**Status**: design draft. Captures the model the verticals (rabble
in-repo, fermi-console as fat client, kask and silat as decoupled
external consumers) currently rely on implicitly. Closes
`docs/OPEN_DESIGN_QUESTIONS.md` §6 from the vertical-decoupling
angle.

---

## 1. The two layers

**ABW harness** (this repo's web surface at `agent-bestiary.world`)
provides the substrate:

- Agents (catalogue, cards, executor, registry, intelligence config)
- Workspaces (composition runtime, git, chat, shared memory)
- Wallets, credits, ledger, gas fees
- Auth (Google OAuth + JWT, API keys, session cookies)
- Observability (eval registry, anomalies, timeline, HITL)
- Marketplace (forks, royalties, listings — Layer 1 today)

**Verticals** are independent surfaces (or fat clients) that consume
the substrate's HTTP/auth contract:

| Vertical | Form | Where it lives |
|---|---|---|
| **rabble** | Web SPA (Flutter) | `rabble.world` (custom-domain mount on same Railway service) |
| **fermi-console** | Native Rust desktop (GPUI) | Distributed as a binary; talks to ABW over HTTPS |
| **kask** | Decoupled — own deployment | External repo; consumes ABW API |
| **silat** | Decoupled — own deployment | External repo; consumes ABW API |
| **harness ops** | Web (this repo) | `agent-bestiary.world` — admin dashboard, observatory, catalogue |

The harness is *not* "rabble + fermi + extras." It's the substrate
plus a thin **harness ops UX** that admins and agent builders use to
see across verticals (catalogue, observatory, admin, agent detail,
wallet). Today these layers are entangled in `dashboard.html`. The
split makes the ops UX explicit and removes vertical-specific
content from it.

## 2. The data segmentation primitive

A workspace is *always* substrate (a row in `teams` plus
`workspace_agents`, gas, git, chat). What makes a workspace "a
rabble swarm" vs "a fermi forecast workspace" vs "a kask
something" is provenance — which vertical created it and which
vertical owns its UX.

Add to `teams`:

```sql
ALTER TABLE teams
  ADD COLUMN IF NOT EXISTS origin TEXT NOT NULL DEFAULT 'bestiary_workspace';
```

Closed enum (extensible, but new values are a deliberate code
change):

- `bestiary_workspace` — created via the harness UX (default)
- `rabble_swarm` — auto-generated by rabble when a swarm is minted
- `fermi_forecast` — created from fermi-console when a forecast is
  published
- `kask_*` / `silat_*` — added when those verticals integrate

**Why a closed-ish enum and not free text:** the harness ops UX
filters and groups by origin. Free text turns the harness into a
metadata janitor. New values land via PR when a vertical is
genuinely new — that's rare and warrants a doc trail.

**Backfill on first deploy of the migration:**

- All workspaces created by `rabble_workspace.rs` flows →
  `origin = 'rabble_swarm'`
- All workspaces created by the fermi-console publish path →
  `origin = 'fermi_forecast'`
- Everything else → keep default `'bestiary_workspace'`

The backfill is best-effort; spot-check via the admin Ownership tab
once landed.

## 3. The substrate API contract verticals depend on

This is what kask, silat, fermi-console, and (post-extraction)
rabble all consume. Keeping it documented prevents accidental
breakage.

**Auth** (session cookies for browser verticals, API keys + Bearer
header for native/external):

- `POST /api/auth/oauth/callback` — Google/GitHub
- `GET /api/auth/me` — current user + role
- `POST /api/keys` / `DELETE /api/keys/:id` — API key management

**Agents** (read-anywhere catalogue + per-user create/edit):

- `GET /api/agents` — list with filters
- `GET /api/agents/:id` — detail
- `POST /api/agents` — create
- `POST /api/agents/:id/execute` — invoke (or `/execute/stream` SSE)

**Workspaces** (the composition runtime):

- `POST /api/workspaces` — create (verticals stamp `origin`)
- `GET /api/workspaces?origin=...` — list, filtered
- `GET /api/workspaces/:id/messages` — chat
- `POST /api/workspaces/:id/messages` — post (`@agent` triggers
  invocation)
- `POST /api/workspaces/:id/budget` — fund
- `GET /api/workspaces/:id/files` — git-backed artifacts

**Observability** (substrate-level, available across verticals):

- `GET /api/observatory/agents/:id/timeline`
- `GET /api/observatory/agents/:id/anomalies`
- `GET /api/observatory/hitl`
- `GET /api/agents/:id/eval/runs` and `/:run_id/signals`

**Wallet** (cross-vertical economy):

- `GET /api/wallets/me`
- `POST /api/checkout/credits` (Stripe)

This list is the minimum. Verticals MAY use more; they MUST NOT
depend on UI routes (`/dashboard`, `/observatory`, `/admin`, etc.)
— those are the harness's own surface and are not part of the
contract.

## 4. Routing model — what is at which URL

Today's reality:

- `agent-bestiary.world` — harness web + JSON API + rabble static
  fallback (host-aware)
- `rabble.world` — custom domain → same Railway service → rabble
  SPA fallback for non-API paths

This is the model going forward. New verticals integrate by either:

- **Subdomain integration** (recommended for branded verticals):
  `kask.yourdomain` → kask's own deployment → calls ABW JSON API
  via `https://agent-bestiary.world/api/*`. Cross-domain auth uses
  the existing fragment-token pattern (see
  `memory/cors-and-deployment.md`).
- **Fat-client integration** (recommended for power tools):
  fermi-console pattern. App ships with its own UI; talks to ABW
  via API + API key per user.

The harness UX itself stays at `agent-bestiary.world` and does NOT
absorb vertical UIs. If you find yourself adding "rabble-only" or
"kask-only" widgets to harness pages, that's a smell — push them
back into the vertical.

## 5. The harness dashboard — what it looks like after the split

Today's `dashboard.html` blocks (with vertical attribution):

| Block | Vertical or harness? | Decision |
|---|---|---|
| Portfolio (forecasting) | fermi (`fermi_forecast` workspaces) | **Move** — to fermi-console or a `/forecasting` harness sub-page. Not on harness ops dashboard. |
| Buy Credits | substrate | **Keep** — wallet is cross-vertical |
| Platform Activity | harness ops | **Keep** — admin/builder rollup |
| Compositions (workspaces) | mixed | **Filter** to `origin = 'bestiary_workspace'` by default; toggle to show rabble auto-gens |
| People | substrate (social) | **Move** — to `/network` per AGENT_MODEL §3 |
| Collection (your agents) | substrate | **Keep** — this becomes the harness ops "My Agents" with per-row observability badges |
| Recent Transactions | substrate (wallet) | **Keep / merge** — fold into Wallet block |

End state — harness dashboard sections (each is an agent home per
AGENT_MODEL §3):

1. **My Agents** — substrate. Per-row: tier, persona_version,
   anomaly count, last eval score, $/run, last-scan-at.
2. **My Workspaces** — substrate. Filter `origin = 'bestiary_workspace'`.
   Toggle reveals other origins (rabble swarms, fermi forecasts) for
   when the admin wants the full picture.
3. **Platform Activity** — substrate. Admin/builder rollup.
4. **Wallet** — substrate. Buy + ledger merged.

Each vertical's own dashboard lives at its own URL:

- Rabble: `rabble.world/dashboard` (already exists)
- Fermi: inside fermi-console (already exists)
- Kask, silat: in their own deployments

## 6. Implementation order

Tight, shippable steps. Each is its own commit/PR.

**Step 1 — Migration + backfill** (foundational, blocks everything).
Add `teams.origin TEXT NOT NULL DEFAULT 'bestiary_workspace'`.
Backfill rabble auto-gens by joining to swarm-keyed identifiers.
Backfill fermi forecasts if a discriminator exists; otherwise leave
default and stamp going forward.

**Step 2 — API filter.** `GET /api/workspaces?origin=foo` filters.
Default behaviour for harness dashboard endpoint is `origin =
bestiary_workspace`. List endpoint exposes `origin` field in
response so vertical UIs can self-filter.

**Step 3 — Create handlers stamp origin.** `rabble_workspace.rs` →
`'rabble_swarm'`. Fermi-console publish → `'fermi_forecast'`.
Direct workspace create from harness → `'bestiary_workspace'`.

**Step 4 — Harness dashboard restructure.** Remove Portfolio,
People, Recent Transactions from `dashboard.html`. Rebuild around
My Agents + My Workspaces + Platform Activity + Wallet. My
Workspaces filtered to `bestiary_workspace`.

**Step 5 — Per-row agent observability badges.** Consume the
endpoints from AGENT_MODEL §5.3 (`/api/me/agents/health` — not yet
built; would land here).

**Step 6 — Move forecasting and people.** Forecasting → `/forecasting`
sub-page (or punt to fermi-console-only). People → `/network`.

Steps 1–4 are the minimum viable decoupling. Steps 5–6 are the
"finish the dashboard refactor" body.

## 7. What this doesn't try to solve

- **Agent visibility per vertical.** Today all curated agents are
  in one catalogue. A rabble-only agent is just a regular agent
  tagged with `rabble`. If we need vertical-scoped catalogues
  later, that's a separate design.
- **Cross-vertical credit accounting.** Credits are platform-wide
  today. A kask user paying credits to invoke an ABW agent is just
  a normal wallet charge — no per-vertical revenue split. If verticals
  need to take a cut, that's a separate design.
- **Cross-vertical auth tokens.** Each vertical handles its own
  user auth and uses ABW API keys (or session for subdomain
  verticals). Single-sign-on across verticals is out of scope.
- **Vertical-specific gas pricing.** All gas comes from the shared
  schedule in `gas.rs`. If a vertical wants to charge differently
  (e.g., rabble subsidises hires), it eats the cost on its own end.

These are explicit non-goals so a later session doesn't lose them.

## 8. Open question this leaves

The only remaining decision the doc doesn't lock: **what to do with
auto-generated rabble workspaces in the user's wallet view**. Every
rabble action that touches an agent moves credits through the
user's wallet → workspace wallet → agent wallet. The user sees
those entries on the harness wallet view today. Post-decoupling
they may want to:

- Stay (current behaviour — full transparency on every credit move)
- Roll up into a single "rabble activity" line per day
- Hide rabble entries by default with a toggle

This is purely a wallet-view filtering decision and doesn't affect
the substrate. Defer to when we ship Step 4.
