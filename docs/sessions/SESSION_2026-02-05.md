## Decisions Made

### Decision 1: Keep `question` not `forecast`
**Context:** User asked if we should support both keywords  
**Decision:** Single keyword (`question`) only  
**Rationale:** 
- Consistency > flexibility
- Avoid "two ways to do it"
- Language name is "Forecasting" but statement is "question you're answering"
- Easier to maintain and teach

**Status:** Accepted

### Decision 2: Update Templates not Parser
**Context:** Templates had old syntax  
**Options:**
- A) Update templates to current syntax
- B) Update parser to support old syntax
- C) Support both

**Decision:** Option A - Update templates  
**Rationale:**
- Current syntax is better (more explicit)
- Parser already implemented and tested
- Breaking change already happened
- Forward compatibility preferred

**Status:** Accepted and implemented

### Decision 3: Add DSL Stability Rule
**Context:** Discovered syntax drift across codebase  
**Decision:** Create strict governance rule for DSL changes  
**Rationale:**
- DSL changes are extremely expensive
- Affects 8+ subsystems
- Need process to prevent future drift
- Protect users from breaking changes

**Status:** Accepted and documented

## Lessons Learned

### 1. Grammar Synchronization is Hard
Manually keeping tree-sitter grammar in sync with parser is error-prone. Consider:
- Generating grammar from parser?
- Automated tests comparing grammar to parser?
- Regular audits?

### 2. DSL Changes are Expensive
This session spent significant time fixing syntax drift. The DSL stability rule will help prevent future issues.

### 3. Templates are User-Facing API
Templates define what users see as "correct syntax". They must be kept current and tested.

### 4. Documentation Prevents Drift
Having canonical syntax documented in PROJECT_RULES.md creates single source of truth.

### 5. Test Everything Together
Parser, grammar, LSP, and templates form a system. They must be tested together, not in isolation.
