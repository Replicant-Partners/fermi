## Decisions Made

### ADR-001: Architecture Option C
**Decision:** Use clean separation of concerns
- FPL Language Server (standalone LSP)
- Fermi Backend (separate Rust service)
- Zed Extensions (UI only, no business logic)

**Rationale:** Loose coupling, independent development, testability

### ADR-002: Rust Backend Rebuild
**Decision:** Rebuild uffp-backend from Node.js to Rust
**Rationale:** Type safety, performance, single-language stack, clean slate

### ADR-003: Hybrid Client-Server (Proposed)
**Decision:** Local execution + backend for agents/collaboration
**Rationale:** Fast local work, rich collaborative features

## Key Insights

### 1. Modular Architecture is Critical
Breaking into 10 clean modules prevents monolithic complexity. Each module has:
- Clear purpose
- Defined dependencies
- Separate documentation
- Independent implementation

### 2. Documentation-First Approach
Spending time on PROJECT_RULES.md upfront will save context loss later. Key elements:
- Session summaries (capture what was done)
- ADRs (capture why decisions were made)
- Module docs (capture how it works)
- TODO.md (capture what's next)

### 3. Context Management is Essential
Without proper documentation:
- Decisions get forgotten
- Rationale gets lost
- Context switching is painful
- Onboarding is impossible

With proper documentation:
- Resume after weeks away
- Understand why choices were made
- Avoid repeating discussions
- Enable collaboration

### 4. Loose Coupling Enables Iteration
By separating LSP, Backend, and Extensions:
- Can swap implementation details
- Can test independently
- Can deploy separately
- Can evolve at different paces

**A:** File-based documentation in `docs/` with Git version control. Use session summaries, ADRs, and module docs.

### Q: Should we use Beads for issue tracking?
**A:** Start with file-based (simpler), add Beads later if needed.

### Q: What's the first module to implement?
**A:** Module 1 (FPL LSP) + Module 2 (Zed Extensions) in parallel.

### Q: How to avoid losing architectural decisions?
**A:** Use ADRs (Architecture Decision Records) for all significant choices.

### Q: When to create ADRs?
**A:** For framework choices, architectural patterns, API contracts, performance trade-offs, user-facing behavior changes.
